## 验收清单

- [ ] 协作站给填了「QQ 命令」的项目各注册一个任务组，工作区是项目文件夹；qq-bot 删掉 `collab` 参数

## 为什么改

qq-bot 现在做两件方向相反的事：

- **通知**：工作台 → 主人。别的插件（协作站的巡检）调 `notify` 主动私聊主人，只发不收
- **派任务**：主人 → 工作台 → agent → 主人。私聊里的一句话交给执行端，agent 做完回报，结果再发回来

两件事共用同一条网关连接、同一套白名单和发消息的规则，但调用方不同，以后要加的功能也不同。派任务这边还有一个限制：一个私聊只有一个会话，日常的事和协作项目的事挤在同一个会话里，上下文互相干扰。

## 插件内部分三块

仍然是一个插件、一个服务 `gwbQqBot`。原因是一个机器人同一时间只能有一条网关连接，被动回复的次数也要在一处统一计数，所以连接只能放在一个地方。

| 块 | 管什么 | 现在对应的文件 |
| --- | --- | --- |
| 连接与收发 | 网关长连接、access token、白名单、被动回复窗口与主动消息、引用原消息、按消息 id 去重 | `qq-gateway.ts`、`qq-rest.ts`、`qq-protocol.ts`、`reply-window.ts` |
| 通知 | `notify`：主动私聊主人、按 id 去重 | 散在 `index.ts`、`rounds.ts`、`chats.ts` 里 |
| 派任务 | 斜杠命令分发、任务组、会话、队列、一轮、回报、懒检查、执行端适配层 | `rounds.ts`、`chats.ts`、`routing.ts`、`executors/` |

依赖方向：通知 → 连接与收发，派任务 → 连接与收发。连接与收发不认识任务组，也不知道通知的存在；收到一条白名单内的私聊后，交给派任务那一块处理。

## 任务组

一个任务组对应一个工作区和一个执行端，在每个私聊里各有一个会话。

| 字段 | 是什么 |
| --- | --- |
| 名字 | 回执里的称呼，也是 `/新会话 <组名>` 的参数 |
| 命令 | 触发它的斜杠命令；默认组没有命令，接收直接发的文字 |
| 工作区 | 已存在目录的绝对路径 |
| 执行端 | `zcode` 或 `claudecode`，必须装着 |
| 提示词附加段 | 写进任务说明的额外要求，比如协作仓要求改动经 `collab.submit` 提交 |
| 空闲时长 | 超过这么久没有新任务，下一条自动开新会话；缺省 6 小时 |

每个私聊的每个组各记一份：当前会话号、在跑的一轮、队列、上一条任务的时间。

组有三种来源：

- **默认组**：每个私聊一个。绑定（`qq-bot.bind`）设的就是这个私聊的默认组；主人私聊没绑时，用设置里的 `default-workspace` 和 ZCode
- **设置里配的组**：给自己常用的目录用，比如 `/论文` 对应论文目录，不用为它写插件
- **插件注册的组**：别的插件经 `gwbQqBot` 注册，插件卸载或重载时自动撤掉

## 一条消息分到哪

只看第一个空白之前的那一段，它必须和某个命令**完全相同**才算命令，不做前缀匹配、不设别名：

| 发来的消息 | 去哪 |
| --- | --- |
| `帮我看下今天的日志` | 默认组 |
| `/mmc 把 DSP 的采样频率改成 20k` | 混合型 MMC 样机的组，任务正文是命令后面的部分 |
| `/新会话` | 默认组下一条起开新会话 |
| `/新会话 mmc` | 混合型 MMC 样机的组下一条起开新会话 |
| `/状态` | 补发没送达的结果；没有的话，列出每个组这一轮在做什么 |
| `/帮助` | 列出保留命令、所有任务组和直接命令，内容按当前注册的现算 |
| `/血糖`（假设有插件注册了这个直接命令） | 插件当场处理，马上回一句，不开会话 |

## 会话

- **默认复用**：同一组的下一条任务接在这一组当前的会话上
- **手动开新会话**：`/新会话 [组名]`
- **自动开新会话**：一个组空闲超过它的空闲时长，下一条任务开新会话，回执里写「已开新会话」
- **改绑、换执行端**：这一组下一条任务开新会话
- **回执带会话行**：比如「mmc · 会话 a1b2 · 第 3 轮」，在手机上能看出是接着做还是新开的
- **不做回到旧会话**：旧会话在 ZCode 或 Claude Code 里还能看到，要接着做就在电脑上接

## 排队

一个组一次只跑一轮，后来的消息排在这一组自己的队列里。不同的组各自排队，可以同时在跑；两个组指向同一个目录时也照样并行，不锁工作区。回执和结果开头都写组名，几个组的结果交错发回来时也分得清。

## 直接命令

插件注册命令名、一句说明和一个处理函数。处理函数拿到命令后面的正文，交回一段要回复的文字，qq-bot 用被动回复发回去。直接命令不进队列，不开会话，也不派给 agent。处理函数抛出的错误把原话回给私聊。

## 命令名规则

- `/帮助`、`/状态`、`/新会话` 是保留字，谁都不能注册
- 重名直接报错，不覆盖、不自动改名：插件注册时和已有的重名，注册方法抛异常；设置里改出一个和已注册的重名，设置校验报错
- 不含空白；长度不超过 8 个汉字或 16 个英文字符，和 QQ 管理端的指令名上限一致，这样每个命令都能放进 QQ 的「/」面板

## QQ 管理端的「/」面板

据[官方文档的「指令配置」与「快捷菜单」两节](https://bot.q.qq.com/wiki/#_9-1-2-指令配置)：

- 指令只能在 QQ 开放平台管理端手动配置，最多 24 个，用于「/」面板和资料卡的「指令」入口；单聊的快捷菜单另外最多 12 个
- 指令名不超过 8 个汉字或 16 个英文字符，说明不超过 15 个汉字或 30 个英文字符
- 没有配置指令的接口；指令也不单独提审，和机器人一起提交审核

所以 qq-bot 的命令以工作台里注册的为准，`/帮助` 按注册情况现算。「/」面板只是手机上省去打字的入口，qq-bot 不同步它，也不依赖它。官方文档没有说明从面板点出来的指令到达时是什么样子：`C2C_MESSAGE_CREATE` 的字段里没有和指令相关的，推测是普通文本消息，要实测确认。

## gwbQqBot 的接口

在现有的 `notify` 旁边加两个方法：

- **注册任务组**：参数是命令、名字、工作区、执行端、提示词附加段，以及可选的空闲时长
- **注册直接命令**：参数是命令、一句说明、处理函数

两个方法都在调用方插件卸载时自动撤掉注册，名字不合规则就抛异常。

## 协作站怎么接

协作站已经可选注入 `gwbQqBot`（巡检通知），依赖方向还是协作站 → qq-bot。改动在协作站的仓里做：

- 协作项目的配置里加一项「QQ 命令」，由人自己起短名（比如 `/mmc`、`/sst`、`/知识`）。填了的项目注册一个任务组，没填的不注册；不从项目名自动截短，项目名可能超过命令名的长度上限
- 工作区是项目文件夹，也就是协作仓的上一级（如 `hybrid-mmc\`，里面并排放着协作仓、资料库、DSP 与 FPGA 代码等仓），agent 能看到整个项目
- 提示词附加段写明：协作仓的改动经 `collab.submit` 提交，其余仓照各自 AGENTS.md 的规矩
- 项目登记或「QQ 命令」变了，就撤掉旧的注册、重新注册
- qq-bot 的 `bind` 删掉 `collab` 参数，qq-bot 里不再有任何和协作站有关的代码

## 聊天表

一个私聊一行，行里按组名各记一份会话、在跑的一轮、队列和上一条任务的时间；没送达的结果仍然按私聊记，每条带上组名。表升第 3 版。读到第 2 版时，把现有的会话、在跑的一轮和队列归进默认组。

## 版本

`bind` 删参数、`qq-bot.status` 的回执形状变了、聊天表升版，这三项都是破坏性改动。动手前读 skill「gwb-release」确认升哪一位，协作站的 peer 范围要跟着改。

## 还没定的

1. **以「/」开头但第一段不是任何命令的消息**：推荐回「没有指令 /xxx」并附上 `/帮助` 的列表，不派出。理由：命令名拼错应该直接报错，不该当成任务派走。代价：真想发以「/」开头的任务文本，要换个写法
2. **只发 `/组命令`、后面没有正文**：推荐回一句用法，不派出
3. **设置里配的组和插件注册的组对哪些私聊可用**：推荐白名单里的所有私聊都能用，每个私聊各记各的会话
4. **从「/」面板点出来的指令到达时是什么文本**：要实测确认
