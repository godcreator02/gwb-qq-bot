**本页回答**：qq-bot 对外提供什么（服务、命令、设置、QQ 里的指令），一条消息怎么变成一轮任务、结果怎么回来，依赖谁，刻意不做什么。

## 功能

手机 QQ 给机器人发一条私聊 → 腾讯投递到 WebSocket 网关（插件常驻这条出站长连接，心跳、断线退避重连、按消息 id 去重）→
白名单校验 → 按斜杠命令分发：`/帮助` 这类保留命令和插件注册的直接命令当场回答，其余文字排进**这个私聊这个任务组**的队列 → 这一组没有在做的一轮就开一轮，交给组的执行端（ZCode 或 Claude Code）→
agent 做完自己调 `qq-bot.report` → 结果按被动回复窗口发回原私聊 → 这一组的队列里还有就接着开下一轮。

只处理私聊：每个人用自己的机器人私聊，群里 @ 机器人不处理。直接发的文字进默认组，`/<组命令> 任务` 进对应的任务组；每个私聊的每个组各有会话和队列，同一组一次只做一轮，不同的组可以同时做，指向同一个目录也会并行。
默认组由绑定设；主人私聊没有显式绑定时，用设置里的默认工作区、交给 ZCode。

### 命令

| 命令 | effect | 用途 |
| --- | --- | --- |
| `qq-bot.status` | read | 连接、各个私聊的绑定、每个任务组的会话、在做的一轮、排队与没送达的结果、最近被拒的 openid |
| `qq-bot.bind` | write | `{chat, workspace, title, agent?, instructions?}`：设一个私聊的默认组，绑到已存在的目录与装着的执行端 |
| `qq-bot.unbind` | write | `{chat}`：解除默认组的绑定 |
| `qq-bot.group.add` | write | `{command, title, workspace, agent, instructions?, idleHours?}`：登记一个任务组，存在聊天表里 |
| `qq-bot.group.remove` | write | `{command}`：删掉命令登记的任务组 |
| `qq-bot.group.list` | read | 全部任务组与直接命令，标明来源 |
| `qq-bot.report` | external | `{round, text}`：执行任务的 agent 交这一轮的结果 |
| `qq-bot.notify` | external | `{id, text}`：把服务方法 `notify` 做成命令给 agent 用，参数原样转过去 |
| `qq-bot.reconnect` | write | 改完 AppID / AppSecret / 旧沙箱接口设置后重连 |

私聊在机器人收到它的第一条消息后才出现在 `qq-bot.status` 里，`bind` 用那里的 `id`（`c2c:<openid>`）。
绑定、改绑、解绑只看默认组：默认组还有在做或排队的任务时拒绝；改绑后默认组下一条用新会话。删任务组在它任何私聊里还有在做或排队的任务时拒绝。参数与回执的逐条说明在随包说明书 `qq-bot`。

### 设置

`app-id`、`app-secret`（走凭据保管）、`sandbox`（缺省 false，true 只兼容旧沙箱接口），这三项改完要 `qq-bot.reconnect`；
`allowed-openids`（每条消息现读，改完即时生效）、`owner-openid`（主人，主动通知的收件人）、`default-workspace`（主人私聊没绑时默认组的工作区）、`idle-hours`（任务组空闲多少小时后下一条开新会话，缺省 6，派任务时现读，不是正数就报错）。

### QQ 里的指令

`/帮助`（按此刻注册的现算：保留命令、全部任务组、全部直接命令）、`/状态`（补发没送达的结果；没有就逐组报空闲，或在做第几轮、排队几条，在做的组做一次懒检查）、`/新会话 [组名]`（那一组下一条起用新会话，不写组名是默认组）。
第一个空白之前的那一段和命令完全相同才算命令；以 `/` 开头却不是任何命令的回「没有指令」、不派出：

{/* ref file="../plugins/qq-bot/src/dispatch/routing.ts" lines="43-63" hash="b1e15f8b5af1" blob="4ba17a7cf705" */}

命令名以 `/` 开头、不含空白，去掉斜杠后汉字等非 ASCII 字符算 2、其余算 1，总长不超过 16，和 QQ 管理端指令名的上限一致；三个保留命令谁都不能注册，和已有命令重名直接报错。

## 任务组与会话

任务组有三种来源：默认组（每个私聊一个，按绑定算）、命令登记的组（`qq-bot.group.add`，存在聊天表里）、插件注册的组（经 `gwbQqBot`，插件卸载时撤掉）。后两种在白名单里的每个私聊都能用，每个私聊各记各的会话。
插件在聊天表读回之前注册了和命令登记的组同名的命令时，派到这个命令的消息回重名、不派出，日志记一行。

下一轮接着用哪个会话：会话记着执行端和工作区，和组现在的定义对不上就开新会话；空闲超过组的 `idleHours`（不给用设置 `idle-hours`）也开新会话，回执里写明：

{/* ref file="../plugins/qq-bot/src/dispatch/group-session.ts" lines="14-20" hash="045fa8fbebcf" blob="df96b60d79d3" */}

回执和结果开头写组名，回执里带一行「会话 a1b2 · 第 3 轮」（会话号的末 4 位、这个会话的第几轮），手机上看得出是接着做还是新开的：

{/* ref file="../plugins/qq-bot/src/dispatch/chat-rounds.ts" lines="273-278" hash="84d2e9084e82" blob="52997d98cc3c" */}

直接命令不进队列、不开会话：处理函数交回的文字按被动回复发回，抛错时回「指令 /xxx 出错：原话」。

## 一轮怎么走

**派出**：从这一组的队列取下一条，定下会话，记下本轮编号、发言人、执行端、工作区和触发消息，再经执行端适配层的 `start` 派出；拿回会话号存进这一组的状态，回「已接收」。
派出失败就把原话回给私聊、这一轮作废，不留「派出未确认」这种要人手工解除的状态——可能已经发出去了的，执行端的原话里会写，人去执行端看。

**提示词**：任务原文后面附来源（QQ 私聊、发言人、任务组的称呼与工作区）、组的要求（组或绑定写了 `instructions` 才有，原样附上）与本轮回报说明。
回报说明写的是 home 名，不写 MCP 服务名——每个 gwb MCP 服务的说明里都写着它连的是哪个 home，agent 照着选，两个 home 各自派出的任务不会报到另一个 home：

{/* ref file="../plugins/qq-bot/src/dispatch/chat-rounds.ts" lines="280-295" hash="e6b1a3e4b0bb" blob="52997d98cc3c" */}

**回报**：本轮编号只用来对上是哪一轮，不当凭证，在所有私聊的所有组里找。同一轮同一段话重交回 `duplicate`，已经结束的轮次交来不同的话拒绝；回执先交回，投递与下一轮在后台做，agent 不用等自己的回报发完：

{/* ref file="../plugins/qq-bot/src/dispatch/chat-rounds.ts" lines="318-334" hash="d13e5c2bbbbe" blob="52997d98cc3c" */}

**懒检查**：没有后台轮询。这一组这一轮还没回报，而人发了 `/状态` 或又往这一组发了一条消息时，才经适配层的 `check` 问一次执行端；做完了却没回报，就按「执行端已结束、没有收到回报」收尾，附上最后的回答，再开下一轮：

{/* ref file="../plugins/qq-bot/src/dispatch/chat-rounds.ts" lines="178-200" hash="5ddcd7de6203" blob="52997d98cc3c" */}

## 聊天表

一个私聊一行。显式绑定写在 `binding`，设的是默认组；主人私聊的默认绑定按设置现算、不写进来。行里按组名各记一份状态（默认组的键是空串）：会话、在做的一轮、队列、上一轮的结果、上一条任务的时间。没送达的结果按私聊记，每条带组名：

整份表按 AppID 存成一份 gwb-data 文档 `chats-<AppID>`，换机器人就是另一份，记录里不写 home 与 AppID。另外记着命令登记的任务组、主人通知的去重、近期处理过的消息 id（网关重推不重复派出）、
每条触发消息已用掉的被动回复次数——`msg_seq` 不能重复，次数先记进表里再发：

## QQ 协议一层

### 白名单

白名单管的是发私聊的人；名单外的消息静默拒绝、只记日志与 `recentRejected`（最多 10 条），不给探测者任何反馈。
官方 API 给的 openid 每个机器人各不相同、不是 QQ 号，首次配置从 `recentRejected` 里取。

### 回复路怎么选

{/* ref file="../plugins/qq-bot/src/qq/reply-window.ts" lines="1-25" hash="9a3354b64365" blob="c063025593d7" */}

窗口与次数是腾讯侧的硬限制（单聊 60 分钟、每条触发消息 4 次），插件只做选择：窗口内、次数没用完走被动回复；窗口外、次数用完或被动发不出去，改发一次主动消息；主动也发不出去，记进没送达、等人发 `/状态` 补发。
测试在 `tests/reply-window.test.ts`。

### 引用原消息

每条回复都带 `message_reference`，在 QQ 里显示成引用它所回答的那条消息：回执引用刚收到的那条，一轮的结果引用派出这一轮的那条，排队、结果交叉出现时也看得出哪条结果对应哪条任务。
「被动回复回的是哪条消息」（`msg_id`，决定被动回复的窗口与次数）和「引用哪条」是两件事：没发出去的结果连同要引用的消息 id 记进没送达，`/状态` 补发时被动回复的 `msg_id` 用这条 `/状态`，引用的仍是当初那条任务：

{/* ref file="../plugins/qq-bot/src/dispatch/chat-rounds.ts" lines="392-396" hash="a7b1426b7e92" blob="52997d98cc3c" */}

引用取不到原消息时照常发正文、只是不带引用（`ignore_get_message_error: true`），结果本身比引用要紧。单聊的被动回复、被动回复引用另一条更早的消息、主动消息带引用，都正常显示成引用（2026-10-07 在机器人 B 上实测）。

### 订阅哪些事件

{/* ref file="../plugins/qq-bot/src/qq/qq-protocol.ts" lines="19-24" hash="705a04f44a90" blob="6a6bf8eff594" */}

单聊事件 `C2C_MESSAGE_CREATE` 在官方的 `GROUP_AND_C2C_EVENT (1 << 25)` 这一位里，订了它群事件也会跟着到达：群事件只记一行事件类型，不进任务；频道事件不订阅。网关在解析和白名单之前记录事件类型，不记录原始载荷。

### REST 与环境

{/* ref file="../plugins/qq-bot/src/qq/qq-rest.ts" hash="60884f70bc28" blob="3a4012a87ac1" */}

鉴权与业务接口用 `api.bot.qq.com`；`sandbox=true` 只兼容旧 `sandbox.api.sgroup.qq.com`。私聊一律发纯文本（`msg_type:0`），回复请求显式转成 `msg_id` / `msg_seq`，业务错误兼容 `err_code` 与 `code`。测试在 `tests/qq-rest.test.ts` 与 `tests/qq-gateway.test.ts`。

## 不做的事

- **不做界面**：状态经 `qq-bot.status` 查
- **不做随手记**（「记：」）：等 gwb-bn-journal 提供往当天日志追加一条的服务后再接
- **不处理群聊**：每个人用自己的机器人私聊，群里 @ 机器人只记事件类型
- **不轮询执行端**：只在人问起时做一次懒检查
- **不自动重发**：派出失败、执行端中断都把原话告诉人，由人决定要不要再派；结果被动发不出去只改发一次主动消息，再不行就等人发 `/状态`
- **不解析 agent 回答的内容**：回报正文原样发回，最多 2000 字，超了让 agent 缩短
